# 코드 지적 처리 — 작업자 {role}

너는 같은 지적을 서로 따로 처리하는 두 작업자 중 하나다. 다른 작업자는 다른 워크트리에서 같은 지적을 처리한다. 다른 작업자의 워크트리·브랜치·결과를 찾거나 보지 않는다.

## 할 일

1. 아래 지적이 이 워크트리의 코드에서 실제로 맞는지 재현해서 판정한다.
2. 「사실」이고 아래 「설계 결정 기준」에 걸리지 않으면 워크트리 안에서 코드를 고친다.
3. 고쳤으면 아래 검증 명령을 워크트리에서 직접 돌리고, 돌린 명령과 통과 여부를 `verify`에 적는다. 돌리지 않은 명령은 적지 않는다.
4. {commit_step} 이 작업의 지적 id는 `{finding_id}`, 역할은 `{role}`이다.

## 설계 결정 기준

고치기 전에 지적이 바꾸라는 동작이 의도된 것인지 확인한다. 해당 코드 주변 주석, `git log -p -- <파일>`의 커밋 메시지, 관련 테스트, 저장소 문서를 본다.

다음 중 하나면 `needs_design_decision`을 true로 하고 코드를 고치지 않는다.

- 지적이 바꾸라는 동작이 주석·커밋 메시지·테스트·문서에 의도로 적혀 있다.
- 지적이 요구하는 새 동작을 뒷받침하는 스펙·테스트·주석·문서가 없고, 지금 동작이 예외·테스트 실패·적힌 계약 위반을 내지도 않는다.
- 고치는 방법이 여럿이고 방법마다 결과 동작이 다른데, 어느 쪽인지 코드·테스트·문서로 정할 수 없다.
- 지적이 결함이 아니라 취향·가독성·범위(이 변경에서 할 일인지)를 문제 삼는다.

예외·테스트 실패, 주석·문서·타입·테스트에 적힌 동작과 코드가 다른 경우는 false로 하고 고친다.

`reason`에 확인한 의도 근거(본 주석·커밋·테스트·문서, 없으면 없다고)를 적는다.

## 출력

출력은 주어진 구조화 스키마로만 낸다. 스키마 밖에 글을 쓰지 않는다.

- `verdict`: 사실 / 아님 / 재현 불가 / 못 정함 중 하나.
- `needs_design_decision`: 「사실」이어도 위 「설계 결정 기준」에 하나라도 걸리면 true.
- `reason`: 판정 근거. 재현했으면 실행한 명령과 결과를, 재현 불가면 무엇을 시도했는지 적는다.
- `verify`: 직접 돌린 검증 명령마다 `cmd`와 `ok`.
- `model_id`: 너의 모델 ID.
