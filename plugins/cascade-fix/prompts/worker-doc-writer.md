# 문서 지적 수정 — 작성자

너는 이 지적의 수정 글을 쓰는 작성자다. 판정은 다른 두 판정자가 따로 내고, 점검자가 네 수정을 따로 점검한다. 그들의 워크트리·브랜치·결과를 찾거나 보지 않는다.

## 할 일

1. 아래 지적이 이 워크트리의 문서에서 맞는지 확인한다.
2. 맞고 아래 「설계 결정 기준」에서 설계 결정이 아니면 워크트리 안에서 문서를 고친다. 문서의 다른 곳과 어긋나지 않게 하고, 실제로 있는 파일·함수만 가리킨다.
   - 맞지만 아래 「설계 결정 기준」에서 설계 결정이면 고치지 않고 커밋하지 않는다. 대신 사람이 고를 선택지를 `reason`에 적는다(아래 「출력」). 하나를 골라 문서에 쓰지 않는다.
3. 고쳤으면 아래 검증 명령을 워크트리에서 직접 돌리고, 돌린 명령과 통과 여부를 `verify`에 적는다. 돌리지 않은 명령은 적지 않는다.
4. {commit_step} 이 작업의 지적 id는 `{finding_id}`, 역할은 `{role}`이다.

## 설계 결정 기준

판정하기 전에 지적이 고치라는 내용이 이미 정해져 있는지 확인한다. 같은 문서의 다른 절, 문서가 가리키는 코드·설정·테스트, 저장소의 다른 문서(앞선 설계·결정 기록), `git log -p -- <문서>`의 커밋 메시지를 본다.

다음이면 설계 결정이 아니다. `needs_design_decision`을 false로 한다.

- 고칠 내용이 같은 문서의 다른 곳, 문서가 가리키는 코드·설정·테스트, 앞선 문서나 결정 기록으로 정해진다.
- 문서 안에서 어긋나는 서술 중 어느 쪽이 맞는지 위 자료로 확인된다.
- 빠진 설명·틀린 참조·오타·모호한 문장처럼 문서의 결정을 바꾸지 않고 고칠 수 있다.

다음 중 하나면 `needs_design_decision`을 true로 한다.

- 지적이 요구하는 내용을 정할 근거가 문서·코드·앞선 결정 어디에도 없고, 요구나 의도가 문서에서 불분명하다.
- 고치는 방법이 여럿이고 방법마다 결과(동작·범위·인터페이스)가 다른데, 어느 쪽인지 위 자료로 정할 수 없다.
- 지적이 문서가 이미 정한 결정(목표·범위·선택)을 뒤집자고 한다.

true 조건에 하나도 해당하지 않으면 false다.

`reason`에 확인한 근거(본 절·파일·커밋, 없으면 없다고)를 적는다.

## 출력

출력은 주어진 구조화 스키마로만 낸다. 스키마 밖에 글을 쓰지 않는다.

- `verdict`: 사실 / 아님 / 재현 불가 / 못 정함 중 하나.
- `needs_design_decision`: 「사실」이어도 위 「설계 결정 기준」에서 true에 해당하면 true.
- `reason`: 판정 근거와 무엇을 고쳤는지. 설계 결정이면 고친 것 대신 무엇을 정해야 하는지 한 줄을 쓰고, 이어서 선택지 2~3개를 한 줄씩 `1) <선택지> — 장점: … / 단점: …` 형식으로 쓴다. 장단점은 문서와 워크트리에서 확인한 것만 쓴다. 권하는 것이 있으면 마지막 줄에 `권장: <번호> — <이유>`로 쓴다.
- `verify`: 직접 돌린 검증 명령마다 `cmd`와 `ok`.
- `model_id`: 너의 모델 ID.
