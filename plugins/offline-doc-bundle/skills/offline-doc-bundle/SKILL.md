# 폐쇄망 문서 배포본 만들기

명령 안의 `<스킬 폴더>`는 이 스킬을 불러올 때 알려 주는 기본 폴더(Base directory)다.

마크다운으로 쓴 문서를 **인터넷이 없는 환경에서 그대로 열리는 묶음**으로 만든다.
받는 사람이 마크다운을 못 읽거나, 메일로 보내야 하거나, 내부망에 반입해야 할 때 쓴다.

## 무엇이 어려운가

단순히 md를 html로 바꾸는 것은 쉽다. 실제로 손이 가는 곳은 따로 있다.

- **다이어그램** — Mermaid를 런타임에 그리면 CDN에서 라이브러리를 받아야 한다. 폐쇄망에서는 빈 화면이 된다.
- **문서 간 링크** — 변환해도 `href`는 `.md`를 가리킨 채 남아 전부 깨진다.
- **되돌아갈 곳** — 문서 35개를 풀어놓으면 받는 사람이 어디서 시작할지 모른다.
- **배포하면 안 되는 문서** — 초안이나 내부 질의 목록은 빼야 하는데, 지우면 그것을 가리키던 링크가 깨진다.

이 스킬은 그 뒷정리를 `scripts/bundle.py` 로 자동화하고, 배포 전에 실제로 열리는지 검증한다.

## 준비 확인

```bash
which marp mmdc          # Marp CLI, Mermaid CLI
ls /Applications/Google\ Chrome.app 2>/dev/null   # macOS 기준
```

**Chrome 경로는 거의 항상 명시해야 한다.** marp와 mmdc는 내부적으로 puppeteer Chrome을 쓰는데, 자체 chromium이 없으면 조용히 실패한다. `--chrome-path`로 시스템 Chrome을 지정하면 다운로드 없이 동작한다 — 폐쇄망에서 특히 중요하다.

프로젝트에 자체 변환 스크립트가 있으면(예: `10. 문서/문서변환/convert_md_to_html.py`) 그것을 쓴다. 팀이 합의한 테마와 옵션이 이미 들어 있어 결과가 일관된다. 없으면 `marp` / `mmdc` CLI를 직접 호출한다.

## 작업 순서

### 1. 발표용 PDF (슬라이드가 필요할 때만)

```bash
python3 "<프로젝트>/convert_md_to_marp_pdf.py" \
  --input "발표자료.md" --output "발표자료.pdf" \
  --subtitle "2026-09-16 팀 회의" \
  --cover-item "배경|현황|설계|결론" \
  --chrome-path "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
```

스크립트가 없으면 `marp --pdf --allow-local-files`. 슬라이드 작성 규칙은 `references/marp.md` 참고 — 슬라이드가 잘리거나 합쳐지는 사고가 여기서 난다.

### 2. 마크다운 전체를 HTML로

```bash
python3 "<프로젝트>/convert_md_to_html.py" \
  --input "<문서 루트>" --recursive --output "<출력>/_html" \
  --mermaid-svg \
  --chrome-path "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
```

`--mermaid-svg`가 핵심이다. 빌드 시점에 SVG로 렌더해 HTML 안에 박아 넣으므로 브라우저가 네트워크를 타지 않는다.

### 3. 링크 치환 + 목차 바

```bash
python3 <스킬 폴더>/scripts/bundle.py link-fix "<출력>/_html"
```

`href`의 `.md`를 `.html`로 바꾸고(앵커 `#절` 보존), 모든 문서 상단에 sticky `← 목차` 바를 넣는다. 여러 번 실행해도 중복되지 않는다.

### 4. 배포 제외 문서 (있을 때만)

```bash
python3 .../bundle.py exclude "<출력>/_html" \
  "To-Be/17.초안.html" "To-Be/18.내부질의.html"
```

파일을 지우고, 그 문서를 가리키던 링크를 **회색 텍스트 + 「미배포」 뱃지**로 낮춘다. 링크가 깨지지 않으면서 "어떤 문서를 근거로 삼았는지"는 그대로 보인다. 근거를 감추면 문서의 신뢰도가 떨어지므로, 지우는 것보다 이 편이 낫다.

### 5. 목차 페이지

```bash
python3 .../bundle.py index "<출력>/_html" --manifest manifest.json
```

`--manifest` 없이 실행하면 디렉터리 구조로 자동 생성된다. 급할 때는 그걸로 충분하지만, **받는 사람이 처음 보는 화면이므로 manifest를 써서 분류와 한 줄 설명을 다는 편이 훨씬 낫다.** 형식은 `references/manifest.md` 참고.

분류는 디렉터리가 아니라 **읽는 사람의 목적**으로 나눈다. "오늘 회의 자료 / 판정 근거 / 배경 분석 / 규정 원문"처럼.

### 6. 검증 — 보내기 전에 반드시

```bash
python3 .../bundle.py verify "<출력>/_html"
```

깨진 내부 링크, 외부 리소스 참조, `<script>` 태그, 깨진 이미지를 찾는다. **깨진 링크 0, 외부 리소스 0**이어야 폐쇄망에서 열린다.

`http://www.w3.org`가 수백 건 잡히는 것은 정상이다 — SVG 네임스페이스 선언이지 다운로드 주소가 아니다. 본문의 법령·기관 링크도 남겨둔다. 클릭할 때만 열리고 페이지 렌더링에는 영향이 없으며, 출처를 남기는 편이 문서의 가치가 높다.

### 7. 압축

```bash
cd "<출력 상위>" && zip -qr "문서모음_YYYYMMDD.zip" _html -x "*.DS_Store"
```

## 놓치기 쉬운 것

**마크다운을 고쳤으면 반드시 다시 변환한다.** HTML만 고치면 다음 변환 때 덮어쓴다. 원본 → 변환 → 검증 순서를 지킨다. 문서 하나만 고쳤어도 그 문서를 가리키는 다른 문서의 링크가 살아 있는지 `verify`로 확인한다.

**여러 군데를 치환하는 스크립트를 쓸 때는 각 치환 직후에 저장한다.** 마지막에 한 번만 파일을 쓰면, 중간의 한 곳이 매칭에 실패했을 때 앞서 성공한 치환까지 전부 날아간다. 실제로 겪는 사고다. 치환 대상이 여러 개면 앵커 문자열을 먼저 `grep`으로 확인하고 시작한다.

**슬라이드 수를 세어본다.** `---` 구분자 하나가 빠지면 두 슬라이드가 한 장에 합쳐지고 아래쪽이 조용히 잘린다. PDF 페이지 수와 마크다운의 `---` 개수가 맞는지 확인한다.

**약어를 풀어쓴다.** RTO, EoS, EUC, GitOps 같은 말은 만든 사람에게만 자명하다. 첫 등장에 괄호로 풀고, 문서 끝에 용어표를 둔다. 받는 사람 중 한 명이라도 비개발자라면 이것만으로 회의 시간이 줄어든다.

**민감 자료가 섞였는지 확인한다.** 사내 규정 원문이나 대외비 문서가 묶음에 들어갔다면, 보내기 전에 수신자 범위를 확인하고 목차 상단에 반출 금지 문구를 넣는다(`manifest`의 `notice`). 외부 저장소에 커밋할 때는 특히 주의한다 — 한번 올라간 것은 히스토리에서 지우기 어렵다.

**메일에는 두 개만 붙인다.** 발표용 PDF와 HTML 묶음 zip. 받는 사람이 zip을 풀고 `index.html`을 열면 되도록 안내한다. 공개 URL이 없는 참고 원본(기관 배포 자료 등)이 있으면 함께 첨부하고, 문서 안에서는 "메일 첨부"라고 밝힌 뒤 **인용한 항목 번호**를 적어 둔다. 어디를 보라는 말이 없으면 첨부해도 읽히지 않는다.
